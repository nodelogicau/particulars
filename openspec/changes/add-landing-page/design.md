## Context

DKF v0.1 was declared and released on 2026-08-26 (tag `v0.1`, GitHub release "DKF v0.1"). The project has no web presence: `particulars.fyi` is registered but has no DNS records, and the only public explanation of the format is the spec README — accurate, but written for implementers and 1100 lines long.

An org repo `particulars-website` already exists (Astro, Cloudflare Pages, newsletter function) targeting the same domain as a company blog; it stalled pre-v0.1 and nothing is deployed. The `particulars-knowledge` repo is a real, public, dogfooded workspace whose current synthesis records the v0.1 release itself.

Target audience: practitioners who use the CLI with an AI harness today, and remote MCP once implemented — not (primarily) format implementers.

## Goals / Non-Goals

**Goals:**

- One static page that a practitioner can absorb in under two minutes, visuals-first.
- Communicate the differentiator — knowledge that evolves through recorded contradiction rather than going stale — without naming any competitor.
- Serve from this repository so the page and the spec cannot drift in ownership; leave the door open for the blog on a subdomain.
- Zero operational surface: no build step, no JS framework, no external requests, nothing to maintain but one HTML file.

**Non-Goals:**

- Blog, newsletter, or multi-page docs site (the `particulars-website` repo remains free to become `blog.particulars.fyi` on Cloudflare later).
- Named competitor comparisons (no OKF or other product names anywhere on the page).
- Remote MCP documentation or promises beyond a single roadmap line.
- SEO campaigns, analytics, or cookie surfaces.

## Decisions

**D1 — Host in the spec repo (`docs/` + GitHub Pages), not `particulars-website`, not a new repo.**
The page describes the format; versioning them together means the page can never be orphaned from what it describes. `particulars-website` is Astro/Cloudflare with a dynamic function — wrong tool for a single static page — and keeping it dormant preserves the blog option at `blog.particulars.fyi` with no domain conflict (apex → GitHub Pages A records; `blog` → CNAME to Cloudflare). Alternatives: reviving the Astro repo (drags Node tooling into one HTML file); new repo (one more thing to own for no benefit).

**D2 — Staleness-led framing: "Knowledge that doesn't go stale."**
Practitioners have not felt "no open format exists" as pain; they have felt an agent confidently reciting a reversed decision. Staleness is the symptom the audience already has; the dialectic is presented as the mechanism, not the hook. Rejected: "shared memory for humans and agents" (weaker differentiation — every memory product claims it); format-led framing à la the README (implementer-oriented). The calendar-format analogy from the README is excluded as too technical for this audience.

**D3 — Differentiate by category, never by name.**
Three categories carry the contrast: notes/wikis (current state only, history is archaeology), vector memory (recall without provenance, nothing is ever superseded), docs with expiry dates (freshness declared in advance, refreshed by overwrite, reasoning evaporates). The third category is aimed at the freshness-metadata approach (e.g. `stale_after`-style fields: staleness *scheduled* rather than *detected and reconciled*) without naming it — naming competitors dates the page and invites feature-by-feature rebuttal. Section kicker, approved during exploration: **"Overwriting loses the why. Appending loses the truth. Reconciling keeps both."**

**D4 — Five sections, fixed order.**
(1) Hero: tagline + the dialectic triad as the hero graphic (thesis/antithesis → synthesis carrying reasoning and declared unresolved, becoming the next thesis). (2) "One fact, two fates": a single everyday fact (deploy day moves) traced through ordinary memory vs particulars — the differentiation panel. (3) The loop: agent recalls/asserts/synthesises on a branch → human reviews a PR (a diagram, not a diff) → merge is acceptance — the conversion moment for practitioners, gets the most visual space. (4) Proof: the real `particulars-knowledge` graph. (5) Quickstart: install/init/skill/recall commands, links to spec, CLI, and live workspace, plus a one-line roadmap strip ("Remote MCP: in design").

**D5 — Hand-authored inline SVG, theme-aware, no runtime.**
Diagrams are inline `<svg>` styled with the page's CSS custom properties, so they follow light/dark via `prefers-color-scheme`; text in diagrams is real `<text>` (selectable, scalable, translatable by the browser). Rejected: mermaid.js at runtime (JS dependency, layout drift); PNG/screenshots (theme-blind, unreadable on retina/mobile, unreviewable in git).

**D6 — Section 4 uses genuine tool output.**
The workspace graph is generated by `particulars export --format mermaid` against `particulars-knowledge`, rendered once to static SVG and captioned with its generation date. The workspace repo is private (it holds personal-scoped claims), so the caption links to the v0.1 release instead of the repo — revisit if a public workspace appears. Practitioners distrust invented screenshots; a real graph whose current synthesis records the release of the spec it is written in is the single most persuasive asset the project owns.

**D7 — Single file, system font stack, no external requests.**
One `index.html` with embedded CSS; no webfonts, no CDN, no analytics. The page makes no network request beyond itself. This is both a performance stance and a privacy stance, and it keeps GitHub Pages configuration trivial.

## Risks / Trade-offs

- [The workspace graph in section 4 goes stale as the real workspace evolves] → It is captioned with its generation date and framed as a snapshot; regenerating it is a one-command task noted in the page's HTML comment. Staleness-with-a-date is honest; a landing page about staleness silently drifting would be the embarrassing outcome.
- [Apex-domain DNS is configured at the registrar, outside this repo] → The exact records (four GitHub Pages A records + optional `www` CNAME) are documented in tasks; the page works at the `*.github.io` URL until DNS lands, so nothing blocks merge.
- [Hand-authored SVG can be fiddly to keep responsive] → Diagrams use `viewBox` with `max-width:100%`; wide diagrams sit in horizontally scrollable containers so the body never scrolls sideways.
- [`docs/` on GitHub Pages requires the default branch] → Already `main`; deploy source is "main / docs". No CI needed, but a broken commit to `docs/` deploys immediately — mitigated by the page being a single reviewable file.
- [Quickstart commands rot if install method changes] → Commands are the published Homebrew tap and current CLI verbs; the spec requires they match the released install path, making drift a spec violation caught at review.
